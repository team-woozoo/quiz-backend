# 퀴즈 생성 품질 기록

AI 연결부터 지금까지 생성 품질을 어떻게 바꿔 왔는지 시간순으로 남긴다. 표본이 적은 측정은 결론이 아니라 관찰로 적는다.

강의 자료 원문, 생성된 문제의 내용, 게이트웨이 주소와 키는 적지 않는다. 자료는 쪽수와 글자 수로만 구분한다.

NORMAL 비율은 그대로 둔다. NORMAL 에서 평가를 빼면 HARD 를 풀지 않는 사용자의 평가 축이 비기 때문이다. NORMAL 의 분석과 평가가 계속 맞지 않으면, 그 유형을 자료 밖 심화 문제 2~3개로 내는 쪽을 검토한다.

## 2026-11-14: 심화 문제 생성과 추론 수준

### 요약

- HARD 는 자료의 원리를 처음 보는 상황에 쓰게 하는 심화 문제로, 근거 문제와 다른 프롬프트로 만든다.
- 생성 프롬프트를 여러 번 바꿨지만 medium 에서는 판정 통과가 회차마다 2~8개로 흔들렸다. 원인은 프롬프트보다 추론량이었다. medium 은 추론 토큰을 126~446 개만 쓰고, 규칙을 읽어도 확인하지 않았다.
- high 는 추론 토큰을 약 1만 2천 개 쓰고 약 80초가 걸리지만, 일찍 멈추지 않았고 분명한 규칙 위반도 드물었다. HARD 만 high 로 생성하는 쪽을 추천한다.
- 같은 자료에서는 같은 문제 씨앗이 회차마다, 한 퀴즈 안에서도 반복된다. 다양성은 추론 수준이 아니라 자료가 정한다.
- 판정 모델이 판정을 한 칸씩 밀어 붙인 일이 두 번 있었다. 판정 응답 검사가 필요하다.
- 호출 단위 타임아웃이 Spring AI 기본값 60초로 고정돼, 설정한 타임아웃이 한 번도 적용되지 않았던 것을 찾았다.

아래 실행은 생성 luna, 판정 Sonnet 이다. "고차원 통과"는 판정 유형이 적용, 분석, 평가 중 하나인 문제 수로, 검토 중인 판정 정책을 적용했을 때의 값이다.

같은 호출에서 근거 문제와 심화 문제를 섞지 않고, 고차원 유형만 따로 만드는 프롬프트를 썼다. 자료 밖 지식은 쓰지 않고 상황만 새로 만든다.

|---|---|---|---|---|
| 부족하면 적게 냄 | 3 (규칙 탈락 1) | 10.9초 | 1,592 | 1/2 |
| 부족하면 적게 냄 | 10 | 22.6초 | 5,183 | 4/10 |

| 긴 규칙 버전 | 10 | 27.6초 | 5,637 | 6/10 |

긴 규칙 버전은 유형마다 필수 조건과 내지 않는 문제를 적고, 문제를 쓰기 전에 근거를 찾고, 쓴 뒤 다시 확인하게 했다. 예시는 경제, 생물, 통계, 코드로 분야를 섞었다.

발견: 부족하면 적게 내라고 하면 세 번 중 두 번을 2~3문제에서 멈췄다. 채우라고 하면 10문제를 내지만 낮은 문제에 높은 이름표를 붙였다. 불일치는 거의 모두 판정이 맞았다. 생성기는 프롬프트의 금지 목록에 적은 꼴(장식으로 붙인 상황, 한쪽이 모든 면에서 나은 비교, 상황에 준 값을 그대로 고르기)을 그대로 냈다.
판단: 규칙 문장을 더 쓰는 것으로는 생성기가 스스로 거르지 않는다. 판정 모델은 매번 정확했다.
조치: 자료 탓인지 확인하려고 자료를 바꿨다.

### 실험 6. 근거 문제 프롬프트에 새 유형 절 적용 (자료 A, medium)

### HARD 불일치 경향 (오후까지 37건)

판정이 생성기보다 낮게 본 경우가 거의 전부였다(이해 25, 기억 5, 평가에서 분석 6, 평가에서 적용 1).

| 패턴 | 건수 | 주로 붙은 이름표 |
|---|---|---|
| 자료 문장이 곧 정답 | 약 11 | 분석, 적용 |
| 조건이 있지만 정답을 바꾸지 않음 | 약 6 | 적용, 분석 |
| 절차나 코드 흐름을 따라가기 | 약 7 | 분석 |
| 이름이나 기능 짝짓기 | 3 | 적용, 분석 |
| 평가인데 한쪽이 모든 면에서 나음 | 4 | 평가 |
| 평가인데 요구마다 대안을 하나씩 짝지음 | 약 6 | 평가 |

분석이 가장 약했다. 생성기는 상황에서 "왜 그런지" 설명하는 문제를 분석으로 붙였다. 평가는 자료에 트레이드오프가 있으면 통과했다(자료 C, high 에서 5/5). 같은 씨앗이 회차마다 반복됐고, 몇 번을 다시 만들어도 심화 문제가 되지 않는 씨앗이 있었다.

### 판정 모델

- 판정을 한 칸씩 밀어 붙인 일이 두 번 있었다. 문제 하나를 건너뛰고 다음 문제의 판정을 앞 번호에 붙여, 마지막 문제의 판정이 비었다(null). 번호로만 짝을 맞추는 지금 구조는 이를 알아채지 못한다.
- 판정이 생성기보다 높게 본 경우가 저녁에 늘었다. 좌표 차이를 계산하는 문제를 세 번, 단계가 여럿인 코드 흐름을 한 번 분석으로 봤다. "여러 값을 이어 계산한다"를 "여러 요소의 관계를 추론한다"로 읽는 것으로 보인다.
- 통과한 문제에도 한쪽이 모든 면에서 나은 평가, 자료 문장이 곧 정답인 분석이 섞여 있었다. 일치율은 실제 품질보다 조금 후하게 나올 수 있다.

### 통과한 문제의 질

정답이 틀린 문제는 없었다. 아쉬운 점은 다음과 같다.

- 한 퀴즈 안에서 같은 주제가 겹친다. 7문제가 실제로는 주제 4개였다.
- 상식으로 지워지는 오답, 문제와 상관없는 오답, 두 선택의 조합으로 만든 보기가 있다.
- 정답을 가르는 근거가 인용에 없는 경우가 있다.
- 정답을 하나로 만들려고 억지 조건을 붙인 경우가 있다.
- 코드 표기(백틱)가 깨진 문제가 있었다.

### 검토 중

- 판정 정책: 심화 문제는 판정이 고차원이면 판정 유형으로 저장하고, 근거 문제도 판정 유형으로 저장하는 안. 판정이 높게 잘못 본 사례(좌표 계산)가 반대 근거다.
- 판정 응답 검사: null 이나 번호 불일치가 있으면 다시 요청한다. 장기적으로는 문제의 앞부분을 함께 받아 대조한다.
- 업로드 적합성 검증: 텍스트를 추출한 뒤 짧은 별도 호출로 학습 자료인지, 난이도별로 낼 재료가 있는지 본다. 명백한 경우만 거부하고 나머지는 안내한다.
- 한 퀴즈 안 중복 걸러내기: 같은 인용이나 같은 청크에서 나온 문제를 하나만 남긴다.
- 오답 규칙 보강: 상식으로 지워지는 보기, 상황과 무관한 보기를 막는다.
- Haiku 4.5 에 추론을 켜고 HARD 를 만들면 high 보다 빠른지.

## 2026-11-15: 판정 모델 종료와 근거 문제 프롬프트 확정

### 요약

- 판정 모델 `bedrock-sonnet`(Claude 3.5 Sonnet v2)이 Bedrock 에서 종료됐다. 판정이 실패하면 생성 유형으로 저장하는 정책 때문에 오류 없이 판정만 빠진 채 저장됐다. 판정 모델을 `bedrock-haiku`(Claude Haiku 4.5)로 바꿨다.
- Haiku 판정은 떨어뜨리는 판단은 정확하지만 통과시키는 데 너그럽다. 추론을 켜면 나아지지만 통과한 고차원 문제의 절반 가까이는 여전히 이름표가 부풀려져 있다.
- 근거 문제 프롬프트의 "근거 찾기" 절은 일찍 멈춤과 관련이 있었다. 근거가 부족하면 한 단계 낮은 유형으로 내라고 고친 버전(v2)으로 확정했다.
- 11/14 의 통과율 비교를 바로잡았다. 판정 모델이 바뀌면 통과율을 비교할 수 없어, 프롬프트 비교는 사람이 같은 기준으로 본 수치를 기본으로 삼는다.

아래 실행은 모두 자료 A, NORMAL, 생성 luna(medium)이다. 판정과 생성 모델이 다른 실행은 표에 적었다.

판정 호출이 `404 NotFound: This model version has reached the end of its life` 로 실패했다. 공지된 종료일은 11/13 이었지만 11/14 저녁까지는 동작했다. 판정 실패는 경고 로그만 남기고 퀴즈는 정상으로 저장돼, 로그를 보지 않으면 알아챌 수 없었다. 생성은 정상이었다.

발견: 같은 키로 생성 호출은 성공해 예산 문제는 아니었다. 판정 모델이 사라져도 서비스가 겉보기에 정상이라 판정 실패를 알아챌 장치가 필요하다.

발견: 한쪽이 모든 요구에서 나은 평가를 두 프롬프트 모두 4/4 통과시켰다. 질문의 겉모양("더 적절한 것은")으로 유형을 정하는 것으로 보인다. 추론 없이 도는 모델은 규칙을 읽어도 대조해 보지 않는다. 생성기 luna medium 에서 본 것과 같다.

### Haiku 판정 (추론 medium)

판정 어댑터에 추론 수준 설정을 붙였다. Claude 는 추론 중에 온도 1 만 받아, 추론을 켜면 온도를 1 로 보낸다. 게이트웨이(LiteLLM)가 `reasoning_effort` 를 Claude 의 thinking 으로 바꿔 판정 로그에 추론 토큰이 650~3,200 찍혔다. 판정은 8~25초 걸렸다.

발견: 떨어뜨린 문제는 거의 모두 정확했다(정답이 준 값 그대로, 자료 코드 그대로의 페이지 수, 원문이 곧 정답인 이해와 분석, 한쪽이 압도하는 평가를 적용으로 내린 경우 포함). 판정 이유가 문제와 맞았고 밀림도 없었다. 그러나 통과시킨 고차원 문제의 약 45%는 이름표가 부풀려져 있었다(원문을 바꿔 말한 이해, 한쪽이 압도하는 평가, 준 값 그대로인 적용). 같은 꼴을 회차마다 다르게 판정하기도 했다.

### Haiku 생성 (참고)

생성기를 Haiku(추론 medium, 온도 1)로 바꿔 5회 돌렸다. 판정도 Haiku 라 통과율은 보지 않았다.

|---|---|---|---|

발견: 일찍 멈춤은 없었다. 대신 인용이 원문에 없거나 개념의 페이지 밖인 문제가 많았고, 자료에 없는 지식을 쓴 문제, 정답이 틀린 문제, 문제에 "청크 11" 같은 내부 번호를 쓴 문제가 나왔다. 같은 자료와 프롬프트인데 입력 토큰은 luna 의 1.7배였다.
판단: Haiku 는 생성기로 쓰지 않는다. 일찍 멈춤은 luna 와 근거 문제 프롬프트의 조합에서 생긴다.

판단: 품질이 같다면 멈추지 않는 v2 로 확정한다. 5회는 작은 표본이라, 일찍 멈춤은 구조(다시 요청)로도 막는다.

### 11/14 비교의 정정

11/14 에 "근거 찾기를 넣은 뒤 NORMAL 통과가 53% 에서 73% 로, 분석이 1/6 에서 4/5 로 올랐다"고 적었다. 이 수치는 실제 Sonnet 판정이다. 그날 Sonnet 이 통과시킨 문제를 같은 기준(사람)으로 다시 보니, 자료 코드 좌표로 사각형 크기를 구하는 문제와 두 줄 출력을 추적하는 문제를 분석으로, 한쪽이 압도하는 두 라이브러리 비교를 평가로, 원문을 바꿔 말한 문제를 이해로 통과시켰다. 같은 기준으로는 6/22(27%)다. Sonnet 이 한쪽이 압도하는 평가를 걸러 낸 것은 HARD 에서였고, NORMAL 에서는 통과시켰다.

판단: 판정 통과율은 판정 모델이 바뀌면 비교할 수 없고, 같은 모델 안에서도 난이도마다 기준이 흔들린다. 프롬프트를 비교할 때는 사람이 같은 기준으로 본 수치를 함께 남긴다.

### 검토 중

- 라벨 허용 정책: 바로 옆 단계로 갈리는 경우(기억과 이해, 이해와 적용, 적용과 분석)는 사람끼리도 갈리므로 받아들이고 판정 유형을 라벨로 저장한다. 두 단계 이상 차이 나면 버린다. 평가는 한 퀴즈에 문제가 적어 가짜 하나가 축 전체를 바꾸고, 판정도 같은 이름표를 붙이는 경우가 있어 별도 보완이 필요하다(판정 프롬프트의 평가 전용 확인, 평가 축은 일정 수가 쌓여야 표시).
- 일찍 멈춤 다시 요청: 받은 문제가 요청의 70% 미만이면 판정 전에 한 번 다시 요청한다.
- 최소 문제 수: 검증 통과가 3개 미만이면 실패로 처리하고 일일 횟수를 차감하지 않는다.
- 판정 실패 감지: 판정 실패가 이어지면 눈에 띄게 남기거나, 서버를 켤 때 판정 모델에 확인 호출을 보낸다.
- 판정 모델: 게이트웨이 답을 받은 뒤 다시 측정한다.
- HARD 만 추론 high 로 생성하는 설정(지금은 추론 수준이 생성 전체에 걸린다).

### Sonnet 5.5 생성, 6-luna 판정

| 생성 | 입력 / 출력 토큰 | 생성 시간 | 저장 |
|---|---|---|---|
| 6회 중 5회 성공 | 16,600 / 17,074~21,957 | 117~147초 | 5, 5, 6, 7, 7 |

실패한 1회는 출력 24,000 상한에 걸렸고 174초가 걸렸다. 추론 토큰은 보고되지 않았지만 10문제에 출력이 2만 토큰 안팎이라, 보이지 않는 추론을 하는 것으로 보인다. 입력은 같은 자료에서 6-luna 의 1.8배다.

발견: 문제의 질은 이날 본 것 중 가장 좋았다. 적용은 거의 모두 새 값을 주거나 원리 두 개를 엮었고, 진짜 트레이드오프가 있는 평가가 한 번 나왔다(나머지 평가는 한쪽이 모든 요구에서 앞섰다). 정답 오류와 자료 밖 지식은 없었다. 그러나 이름표를 한 단계 높게 붙였다. 판정이 떨어뜨린 문제는 원문이 곧 정답인 "이해"(기억으로), 계산 단계가 여러 개인 "분석"(적용으로), 한쪽이 앞서는 "평가"(적용으로)였고, 문제 자체는 대부분 좋은 기억·적용 문제였다.

한 단계 차이를 받아들이고 판정 유형으로 저장한다고 가정하면(두 단계 차이는 버림) 처음 3회는 9, 8, 10개가 남는다. 그러나 유형은 기억 12, 이해 0, 적용 14, 분석 0, 평가 1 로 쏠린다. 이름표가 한 칸씩 내려가면서 이해와 분석이 모두 사라진다.

판단: 지금 구조에서는 Sonnet 을 생성기로 쓰지 않는다. 시간(출력을 나눠 병렬로 보내는 방법)과 이름표(생성 프롬프트에 유형별 "해당하지 않는 경우"를 맞추는 방법)를 먼저 풀어야 한다. 라벨 허용 정책은 이름표가 정직해진 뒤에 의미가 있다.

### 잘린 응답 처리

Sonnet 이 출력 상한에 걸린 회차는 "응답을 해석하지 못했다"가 아니라 "생성 완료, 받은 문제 0개"로 기록되고 `NO_VALID_QUESTIONS` 로 끝났다. 게이트웨이가 Claude 의 구조화 출력을 도구 호출로 바꾸면서, 잘린 응답을 깨진 JSON 대신 빈 객체로 돌려준 것으로 보인다(원문은 남지 않아 추정). 6-luna 는 잘리면 깨진 JSON 이 와서 제대로 실패로 기록됐다. 파싱 성공 여부가 아니라 끝난 이유(length)와 빈 결과로 실패를 가려야 한다.

| 생성 모델 설정 | 이미지 기본값만 | compose 가 `LLM_MODEL` 을 넘겨, 게이트웨이가 모델을 바꾸면 배포 없이 서버 설정으로 바꾼다 |

### 검토 중

- 유형별 분리 호출: 유형마다 따로 요청해 병렬로 보낸다. Sonnet 생성에서는 출력을 나눠 시간을 줄이는 가장 직접적인 방법이다. 입력이 호출 수만큼 늘어 프롬프트 캐싱이 필요하고(게이트웨이 지원 확인 필요), 호출 사이의 중복을 막으려면 개념을 나눠 주어야 한다.
- 업로드할 때 개념 추출: 지금은 문제가 나온 개념만 저장돼 자료 전체의 개념을 모른다. 업로드 뒤 개념을 미리 뽑아 두면 병렬 호출에 개념을 나눠 줄 수 있고, 아직 안 나온 개념을 먼저 요청해 씨앗 반복을 줄일 수 있다.
- 잘린 응답을 생성 실패로 처리한다(끝난 이유 length 또는 빈 결과).
- 게이트웨이에 Sonnet 의 추론 설정과 프롬프트 캐싱을 문의한다.

## 2026-11-19~20: 유형별 단독 요청과 유형 정의 개편

### 요약

- 병렬 생성을 하기 전에, 유형 하나만 요청했을 때 걸리는 시간과 이름표를 쟀다. 가장 느린 유형도 40초 안팎이라 병렬이면 Sonnet 생성 시간을 감당할 수 있어 보인다.
- 단독으로 요청해도 이름표 부풀림은 그대로였다. 기억과 적용은 정직했고, 이해와 분석은 한 단계 높게, 평가는 한쪽이 앞서는 비교로 부풀렸다.
- 생성 프롬프트의 유형 정의를 블룸 분류(Anderson & Krathwohl, 2001)의 하위 과정에 맞춰 다시 쓰고, 판정 프롬프트를 같은 문장으로 맞췄다. 판정은 사람 기준과 거의 같아졌다.
- 이해와 분석은 프롬프트를 고쳐도 코드 위주 자료(A, C)에서 거의 나오지 않았고, 자료 D 에서는 분석이 진짜로 나왔다. 이제 병목은 프롬프트가 아니라 자료의 질이다.
- 평가는 프롬프트 예시가 문제였다. 예시를 바꾸자 4회 중 1회에서 4회 모두 통과로 올랐다.

### 조건

생성 Sonnet 5.5, 판정 6-luna(추론 기본값, 온도 0), 생성 출력 상한 24,000. 유형 하나만 요청하도록 문제 수와 유형 비율을 실험용으로 바꿔 돌렸다(기억 2, 이해 2, 적용 3, 분석 2, 평가 1). 품질은 사람이 같은 기준으로 봤다.

### 유형별 단독 요청 시간

| 유형 (문제 수) | 생성 시간 |
|---|---|
| 기억 (2) | 약 17초 |
| 이해 (2) | 19~21초 |
| 적용 (3) | 33~37초 |
| 분석 (2) | 32~38초, 예시 내용을 문제에 보여 주게 한 뒤 43~73초 |
| 평가 (1) | 18~20초 |

병렬로 보내면 가장 느린 호출 기준으로 40~45초가 예상된다. 11/17 의 Sonnet 한 번 호출(117~147초)보다 짧다. 분석은 문제에 코드나 사례를 직접 넣게 되면서 길어졌다.

### 유형 정의 개편

생성 프롬프트와 판정 프롬프트를 같은 틀로 바꿨다. 유형마다 필수 조건, 하는 일(블룸 하위 과정), 내지 않는 문제와 그때 맞는 유형, 예시, 잘못된 예 순서다.

- 이해: "개념의 의미를 해석해 판단한다". 정답이 개념에 대한 판단이어야 하고, 상식만으로 풀리면 안 된다. 사례를 붙였지만 원문을 떠올리거나 규칙을 돌리면 풀리는 문제는 기억이나 적용이다.
- 이해와 적용 가르기: 정답이 개념에 대한 판단이면 이해, 규칙을 실행한 결과(값, 위치, 출력, 동작)이면 적용이다. 같은 상황으로 두 문제를 나란히 보여 준다.
- 적용과 분석 가르기: 계산 단계 수로 가르지 않는다. 분석은 부분 사이의 관계를 밝혀야 한다.
- 분석: 구별하기(그럴듯한 다른 원인 사이에서 실제 요인 가려내기)와 조직하기(부분의 역할과 영향 밝히기). 자료가 이미 정리한 구조를 다시 고르게 하면 기억이고, 정답이 최종 동작이나 값이면 적용이다.
- 평가: 하나만 고르게 만드는 이유가 있어야 하고(나눠 쓰거나 함께 쓸 수 없음), 정답이 어떤 요구를 포기하거나 미뤄야 한다. 모든 대안이 쓸 수 있는 것이어야 한다.
- 예시 내용 보여 주기: 학생은 자료를 볼 수 없으므로, 문제가 사례·실험·지문·표·코드에 기대면 필요한 부분을 문제에 보여 준다. 이름만 가리키면 판정은 기억으로 본다.
- 예시는 특정 분야에 치우치지 않게 경제 상황 하나로 이해·적용·분석을 나란히 보였다.

### 결과

| 유형 | 자료 | 결과 |
|---|---|---|
| 이해 | C | 판정이 사람 기준과 8/8 일치. 진짜 이해는 적었다. 생성기가 가장 눈에 띄는 씨앗 하나에 몰렸다 |
| 이해 | D | 자료 A, C 보다 나았지만 씨앗이 여전히 하나로 몰렸다 |
| 분석 | A, C | 진짜 분석 0~2/8. 코드를 따라가는 문제(적용)나 메서드 역할을 떠올리는 문제(기억)로 떨어졌다 |
| 분석 | D | 판정 통과 5/8, 모두 사람 기준으로도 진짜 분석이었다(한 결과에 작용하는 여러 요인 가운데 실제 요인 가려내기) |
| 평가 (이전 예시) | D | 1/4. 정답이 모든 요구에서 앞서는 대안이었다. 이전 프롬프트 예시 자체가 그런 꼴이었다 |
| 평가 (새 예시) | D | 4/4. 다만 요구의 우선순위가 문제에 거의 드러나 있어 쉽고, 문제 모양이 비슷하다 |
| 기억 (회귀) | A | 4/4 |
| 적용 (회귀) | A | 5/6. 빠진 1개는 판정이 아니라 인용이 개념에 없어 규칙 검증에서 빠졌다 |

판정이 경계 문제에서 흔들리는 경우가 있었다. 같은 꼴의 분석 문제를 회차마다 다르게 봤고, "다음 단계로 미룬 요구"를 요구로 볼지 갈렸다. 판정 프롬프트에 "미룬 요구도 요구다"를 넣은 뒤로는 같게 판정했다.

발견:

- 이름표 부풀림은 정의 문장만으로 다 고쳐지지 않는다. 자료에 그 유형의 재료가 없으면, 프롬프트의 "반드시 모두 낸다"(5곳)에 밀려 생성기가 낮은 유형의 문제에 높은 이름표를 붙인다.
- 분석은 여러 요인이 함께 작용하는 내용이 있어야 나온다. 이해는 개념 짝(비슷하지만 다른 개념)이 있어야 하고, 생성기가 씨앗 하나에 몰리지 않게 개념을 나눠 줘야 한다.
- 평가는 자료보다 프롬프트 예시의 영향이 컸다.

판단: 프롬프트는 여기서 멈추고 구조로 간다. 업로드 때 개념을 뽑고 자료가 어떤 유형의 재료를 가졌는지(정의, 개념 짝, 규칙, 함께 작용하는 요인, 대안) 분류해, 병렬 호출에 개념과 유형을 나눠 준다. 유형별 호출에서는 재료가 없으면 적게 내라고 한다.

11/17 같은 조합(6~7개)보다 적다. 생성 쪽은 그대로다. 출력은 16,000 상한까지 여유가 있고, 평가는 이번에도 생성기가 분석으로 내렸다. 줄어든 것은 판정 쪽이다.

- 적용으로 낸 문제 중 정답이 문제에 보여 준 코드에 그대로 있는 4개를 판정이 모두 떨어뜨렸다. 11/17 에는 Sonnet 판정이 이 꼴을 통과시켜, 저장된 적용 14개 중 약 6개가 이런 문제였다.
- 분석으로 낸 6개는 모두 떨어졌다(좌표 따라가기, 메서드 역할 떠올리기). 자료 A 에는 진짜 분석이 없었다는 11/17 결과와 같다.
- 이해 2개는 원문 문장을 그대로 옮긴 답이라 기억으로 떨어졌다. 다만 같은 꼴의 문제가 1회차에서는 이해로 통과해, 판정이 흔들린 사례다.

떨어뜨린 12개는 사람 기준으로도 맞다. 저장 수는 줄었지만 통과한 문제의 이름표는 더 정직해졌다. 2회차는 3개로, 최소 문제 수(3개 미만 실패)의 경계에 있다.
